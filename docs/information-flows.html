Practice Site Data Flows

davidsteinberg.com rebuild · as deployed on 27 October 2026 · Civic template on Firebase Hosting and GitHub Pages, backend on Firebase project davidsteinberg-site

Four flows share one Google Cloud project. The public site sends nothing but anonymous counts; the consultation form is the first place personal information enters, and it goes two ways at once (Firestore and Gmail). The portal and dashboard sign in through Google and talk to Firestore directly under security rules, with four small functions for the steps that need server trust.

What never leaves the browser or is never kept

  • The visitor's address: pageHit hashes it with the browser string, the day and a server-side salt, keeps the hash for that day's unique count, and discards the address. The rate limiter keeps a per-address counter for an hour.
  • Cookies: none on the public site, the portal or the dashboard. Firebase Auth keeps its session in the browser's own storage.
  • Client names in clinical data: clients/ and responses/ hold the pseudonym and the uid; the name and email exist only in Firebase Authentication and appear in the dashboard through an audited function call.
  • Nothing goes to a third-party analytics or email-marketing service.

Outside the BAA today to close

  • Firebase Authentication holds client identities but is not on Google's covered-products list; Identity Platform is. One-click upgrade in the Firebase console, no code change.
  • Gmail (consumer) receives the full consultation request. Either reduce the email to a bare "new request from [name]" ping, or send through an account with a BAA (Google Workspace) or a transactional service on the practice domain.
  • The BAA itself is not yet accepted on project davidsteinberg-site. Firestore, Cloud Run functions, Secret Manager, Cloud Logging and Build are covered once it is.
  • Hosting (Firebase Hosting, GitHub Pages) is not covered and does not need to be: it serves the pages; no personal data passes through it.
